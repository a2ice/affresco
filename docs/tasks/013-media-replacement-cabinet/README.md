# 013 — Явная замена при лимите и удаление исходных изображений

Дата: 2026-10-29. Запрос владельца: после достижения лимита 1 гостевая / 3 аккаунтных фрески заменить «Применить» на «Заменить текущее» и позволить удалять исходные фото фресок и комнат в кабинете.

## Решение

- Лимиты **отдельны** для `fresco` и `room`: 1 на гостевую PHP-сессию и 3 на аккаунт. Ни новые учётные записи, ни регистрация не добавляются.
- При полном лимите загрузка без `replace_id` возвращает `409 media_limit_reached` **для гостя и аккаунта**. Автоматическое удаление гостевого фото убрано.
- В popup «Моя фреска» пользователь видит прежние изображения, выбирает заменяемое (для одного гостевого файла выбор предустановлен), кнопка становится «Заменить текущее». При трёх файлах выбор обязателен.
- Клиент передаёт только ID собственного заменяемого файла. Сервер под блокировкой JSON подтверждает принадлежность **этому пользователю и типу**; чужой/уже удалённый ID → `409 replace_target_not_found`, старый файл остаётся нетронут. Новый JPEG сохраняется и metadata заменяется, после этого удаляется старый JPEG. Сбой сохранения metadata не удаляет старое изображение.
- В списке сохранённых комнат редактора, если квота заполнена, появляются отдельные действия «Заменить» у каждого файла, а общее действие «Загрузить» скрывается. Для комнаты аналогичный `replace_id`.
- Кабинет → «Генерации»: уже существовавшая секция «Мои фрески» и новая «Мои комнаты». В обеих миниатюра, название, счётчик использования и крестик удаления с подтверждением. Удаление инициирует текущий `media.php?action=delete`, перерисовывает галереи и освобождает место в квоте. **Исходные фото** отделены от AI/ручных **результатов** примерки. Других пользователей не затрагиваем.

## 2026-10-29 — корректировка после production FAIL (загрузка авторизованного пользователя)

Владелец прислал два скриншота: аккаунт `admin`, выбор разных JPEG/PNG, кнопка «Применить», ошибка «Не удалось сохранить изображение». Это **FAIL для пользовательского сценария загрузки**, даже при успешном прежнем CI.

Диагностика отдельным изолированным guest-запросом на production (GitHub Actions [#40882503227](https://github.com/a2ice/affresco/actions/runs/40882503227)) показала `POST /api/media.php` → HTTP 201 и удаление собственного синтетического JPEG → HTTP 200. Следовательно, массовый сбой endpoint не подтверждён; ошибку именно авторизованного аккаунта без его сессии проверить не удалось. Прежний интерфейс маскировал ошибки типа `invalid_image`/`invalid_action` и non-JSON HTTP.

Техническое устранение потенциального сбоя записи аккаунта: `media_assets` больше не модифицирует исходный `data/accounts.json`, который нужен только для удостоверения личности и может быть read-only у PHP. Новая каноническая запись — в `af_state(account_id)`, там же, где избранное и черновики. Старые записи из `accounts.json` импортируются лениво при первой модификации; пустое сохранённое значение имеет приоритет над legacy (удалённый файл не возрождается). Отдельное guest-хранилище без изменений. Обработка ошибок `site.js`, `tryon.js`, `tryon-library.js` уточнена; при расхождении квоты список пересчитывается.

Проверки: реальный HTTP integration test на локальном сервере с `chmod 0444 data/accounts.json` для авторизованного пользователя и с миграцией legacy metadata; тесты удаления без возрождения старых изображений. Синтетический production probe удалён из кода после сбора ответа.

**Статус:** исправление в [PR #37](https://github.com/a2ice/affresco/pull/37), независимый E2E с действительной пользовательской авторизацией ещё требуется. Не утверждать, что production-ошибка устранена до браузерной проверки аккаунта.
