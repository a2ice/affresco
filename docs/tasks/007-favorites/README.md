## Область изменений

Владелец согласовал обновление мобильной галереи перед реализацией избранного:

1. Ссылка **«Как выбрать свой кадр»** перенесена на Hero непосредственно под CTA **«Выбрать фреску»**, ведёт к `#try`; перед панелью коллекции её больше нет.
2. Панель со статусом («Показано N из M»), иконкой обновления и мобильным переключателем **1 карточка / 3 карточки**.
3. На телефонах (ширина до 600px) панель использует `position:sticky;top:70px`, то есть доходит до нижней границы фиксированного хедера. Панель живёт внутри контейнера секции коллекции, поэтому перестаёт быть sticky после выхода из этой секции. Desktop использует обычную панель и сетку из 3 карточек; 601–900px без мобильного переключателя остаётся адаптивная сетка из 2 карточек.
4. Исходный мобильный режим **одна крупная карточка в ряду**, альтернативный — **3 миниатюры в ряду**. Выбор запоминается в `sessionStorage` этого браузера, подгрузка по 6 карточек и `IntersectionObserver` сохраняются.
5. Кнопка обновления каталога оформлена как квадратная кнопка-иконка, рядом с переключателем (одинаковая высота).
6. В шапке размещено **всегда контурное** чёрное сердечко со счётчиком и кнопкой открытия отдельного **попапа «Избранное»**; на каждой карточке отдельная кнопка-сердечко. Не делать кнопку-сердечко вложенной в кнопку открытия редактора — карточка теперь `article`, внутри отдельные независимые `button.catalog-open` и `button.catalog-fav`.
7. Успешное добавление: возвращённый сервером артикул появляется в избранном, сердечко закрашено чёрным, счётчик увеличивается. Удаление — контурное сердце, счётчик уменьшается. Состояние загружается при открытии страницы. Ошибка сервера не приводит к ложному закрашиванию.
8. Нажатие на сердечко в шапке **не фильтрует каталог и не закрашивает сердечко**, а открывает окно «Избранное» с именами, миниатюрами, SKU, удалением и переходом в редактор. Гостю показывается кнопка «Авторизоваться», открывающая существующий попап входа. Кнопка «Перейти к коллекции» возвращает ко всем карточкам. Для ошибок API есть повторная загрузка.

### Исправлена подгрузка по 6 и поведение кнопки «Показать ещё» (28.10.2026)

**Дефект:** при переходе к якорю `#try` выше загружался пакет картинок, но JS ранее блокировал добавление последующих карточек по постоянной проверке `location.hash==='#try'` и показывал ручную кнопку даже после возвращения в каталог. Та же кнопка была видна при нормальной прокрутке, хотя требовался `IntersectionObserver`.

**Изменения:**
- В обычном режиме с `IntersectionObserver` **кнопка скрыта**, следующая партия из шести карточек добавляется автоматически при достижении sentinel. Элемент sentinel остаётся в DOM для наблюдения.
- Если посетитель перешёл напрямую к `#try`, `#how` или `#about` (клик по якорю / открытие страницы с hash), галерея переходит во временный `catalogManualMode`: авто-загрузка не запускается во время якорной прокрутки, **«Показать ещё»** остаётся доступной как ручное действие. У ручной кнопки убрана стрелка.
- При скролле **назад в коллекцию** (`#catalog` пересекается с viewport) режим становится автоматическим, кнопка скрывается, `IntersectionObserver` снова подключается. Оставшийся `#try` в адресе **не может** заблокировать ни явную ручную загрузку, ни нормальное возвращение.
- Для старых браузеров без `IntersectionObserver` кнопка доступна постоянно, если карточки ещё есть.
- Асинхронная auto-партия, начатая непосредственно перед глубоким переходом, отменяется до добавления в DOM; ручная партия не отменяется этим правилом. Ресурс `site.js?v=lazy-gallery-deeplink-20261028`.
- `public/data/catalog.json` не меняли: владелец независимо добавляет названия/размеры/описания по артикулам.

**Проверка кода:** JavaScript компилируется, симуляция пяти переходов между manual/auto/complete — PASS 5/5; асинхронные сценарии manual add, auto add, отмена auto во время deep link и последняя неполная партия — PASS 4/4. Публичную версию нужно проверить после деплоя и подтвердить Safari iPhone: scroll к `#try` без скачка, вручную «Показать ещё» ниже галереи добавляет шесть, возвращение вверх/обычный скролл вниз снова автоматически добавляет шесть без постоянной кнопки. **Независимый E2E пока не подтверждён**.

## Хранилище и разделение аккаунтов

Временный серверный API: `public/api/favorites.php`.

- `GET /api/favorites.php` → `{items:[sku],count:number,scope:"guest"}`.
- `POST /api/favorites.php`, JSON `{action:"add"|"remove",sku:"6039"}` и `X-Affresco-Request: 1` → актуальный список/счётчик.
- Случайный ключ гостя находится **только в PHP-сессии**, управляемой HTTP-only SameSite=Lax cookie; на клиент он не передаётся.
- JSON каждого гостя записывается за пределами публичного `public/` (или во внутренний системный temp, если директория хостинга недоступна), файлы имеют права `0600`, при записи используется `flock()` для предотвращения гонок. Значения — исключительно валидированные артикулы, лимит 200.
- Гостевые данные **не переносить автоматически** в будущий аккаунт. После входа frontend должен получать только account favorites из отдельной приватной базы, после выхода — снова гостевые. До реализации 004 endpoint при наличии `afreska_user_id` намеренно возвращает `501 account_favorites_not_ready` вместо смешивания гостевого/аккаунтного списка.
- Изменение PHP-сессии в `public/api/session.php`: согласованный срок cookie 30 дней, httpOnly/SameSite, для согласованности с сохранением гостевого ключа. **Гарантия сохранности зависит от политики очистки PHP-сессий на хостинге**; постоянную account-базу и logout/login предстоит сделать в 004.
- Никакие user JSON или файлы с приватными ключами не входят в Git. Публичен только PHP-код API.

## Исправлено по жалобе на toast без счётчика — 28.10.2026

**Корневая причина:** PHP при формировании `$items[$sku]=true` превращает цифровые строковые ключи вроде `"6039"` в целые числа. Следующий `array_keys($items)` отдавал JSON-массив `[6039]`, хотя клиент использует строковые SKU и `filter(safeSku)` отбрасывал число. Поэтому POST подтверждался и показывался toast, но `favorites.size` и заливка сердца оставались нулевыми. Предыдущие mock-тесты ошибочно возвращали только строковые SKU и этого не выявили.

**Исправления:**
- `public/api/favorites.php`: как сохранение, так и ответ API формируют строки через `array_map('strval',array_keys($items))`; чтение поддерживает старые сохранённые цифровые значения.
- `public/api/account-state.php`: аналогичная сериализация строк и нормализация старых числовых SKU для аккаунта.
- `public/assets/js/site.js`: перед `safeSku` приводит числа обратно к строкам через уже существующий `normalizeSku`; `account.js` нормализует список в кабинете. Обновлены версии JS в `index.html`.

**Проверено:** PHP CLI воспроизводит проблему (`array_keys` → `[6039,6247]`) и результат исправления (`["6039","6247"]`). Изолированные сценарии с намеренно **числовыми** ответами backend для гостя/аккаунта: 0→1→0, сердце карточки false→true→false, попап 0→1→0, два последовательных POST add/remove — PASS. Независимый браузерный E2E всё ещё открыт. Не считать предыдущий успешный toast подтверждением изменения счётчика без просмотра реального ответа и состояния UI.
