# 006 — Отправка выбранного кадра фрески на email

**Статус на 28.10.2026:** код реализован в `main`, приёмка реального письма в почтовом ящике и browser E2E **ещё не проведены**. Не заявлять доставку без подтверждения.

## Работающий сценарий

В редакторе вместо неинформативного «Сохранить» (кадр сохраняется автоматически) размещена кнопка **«Отправить»** с конвертом. По нажатию открывается email-попап `#emailModal`: пользователь вводит email; авторизованному посетителю адрес предзаполняется из `data/accounts.json`, но доступен для редактирования.

После отправки в браузере создаётся **настоящий JPEG выбранного кадра** через Canvas из оригинального изображения с учётом текущего zoom/положения/selection. Максимальное измерение файла — 1600 px, качество JPEG 0.80, жёсткое ограничение base64. В JSON POST на `/api/send-crop.php` уходят только email, SKU, размеры кадра и JPEG. Почтовый PHP формирует MIME multipart/mixed (текст, SKU, размеры, изображение как вложение `affresco-SKU.jpg`) и вызывает `mail()`. Окно успеха открывается **только при `HTTP 200` и `accepted:true`**; это означает приём PHP-почтовым транспортом, но не гарантирует финальную доставку в Inbox. При ответе 503 и прочих ошибках попап остаётся на экране и показывает понятную ошибку. Никакой имитации и фиксированного таймера успеха больше нет.

Без входа в систему пользователь может отправить кадр на свой адрес, но не сохраняет его в аккаунте. Для вошедшего пользователя сервер при отправке обновляет `email` в существующей записи `accounts.json`, используя блокировку файла. В личном кабинете появилась отдельная форма для редактирования и сохранения `email` через `POST /api/account-email.php`; `GET /api/auth.php` возвращает сохранённый адрес только владельцу авторизованной сессии. Пароли, хеши и полный JSON никогда не возвращаются.

### Ограничения и безопасность

- Запись `data/accounts.json` осуществляется на FTP в существующем месте; новый ключ `"email": "example@domain.tld"` создаётся у конкретной записи при первом сохранении. Значение не нужно вручную добавлять всем пользователям.
- Для отправки используется штатный PHP `mail()`. Требуется **настроенный исходящий почтовый транспорт на хостинге**, а для доставляемости — корректный SPF/DKIM/DMARC. По умолчанию адрес отправителя `no-reply@affresco.a2ice.ru`, можно переопределить через переменную сервера `AFFRESCO_MAIL_FROM` (валидный адрес в своём домене). Никаких SMTP-паролей в репозитории.
- `send-crop.php` принимает только POST с `X-Affresco-Request:1` и проверкой Origin/Fetch-Site, валидирует email/SKU/числа и содержимое JPEG. Размер файла ограничен 2.2 MB, измерения изображения — до 3200 px. Не более **4 попыток за час на IP** в приватном PHP temp storage. Не использовать этот endpoint как массовую рассылку.
- `/data/accounts.json` должен возвращать HTTP 403 при прямом запросе; хеши на FTP и email остаются серверными. `public/data/.htaccess` защищает файл на Apache, конфигурация nginx требует отдельной проверки.
- `mail()`=true означает **приём почтовым транспортом**, а не подтверждение доставки в почтовый ящик. Нельзя показывать пользователю «доставлено».

## Проверено

- Синтаксис нового JS корректен; изолированные проверки Canvas-кропа: весь кадр, уменьшенный кадр и обрезка у края — 3/3 PASS.
- Мок-сценарии submit: адрес из аккаунта подставлен, редактирование возможно, POST содержит JPEG, success only on positive API response, error leaves dialog open — PASS.
- Внешним GET оба новых PHP endpoint возвращают 405 (т.е. файл развёрнут, исполняется PHP и GET запрещён), `auth.php` без входа возвращает `authenticated:false`.
- **Не проверено:** реальная отправка `mail()`, доставка тестового JPEG на живой адрес, запись `email` в FTP `accounts.json` после авторизованного изменения, UI на iPhone Safari. Не передавать логин/пароль или личный email в документацию.

## E2E handoff для независимого тестирования

Проверять `https://affresco.a2ice.ru/`, коммиты `main` с версиями `site.js?v=email-live-20261028` и `account.js?v=account-email-20261028`.

1. Гость: открыть 6039, выделить узнаваемый фрагмент, выбрать «Отправить», указать **тестовый email**. На тестовом адресе получить письмо с JPEG и убедиться, что прикреплён именно выбранный, а не целый исходный рисунок.
2. Войти под тестовым аккаунтом с `password_hash()`, сохранить email через кабинет, обновить страницу, снова нажать «Отправить» — адрес должен подставиться. Изменить адрес в email-попапе, отправить, проверить обновление `accounts.json` и подстановку при следующем открытии.
3. Вызвать ошибку почтового транспорта в тестовом окружении — success недопустим, остаётся форма и сообщение об ошибке. Проверить формат 422 для неверного email, 429 для >4 отправок/час/IP; проверить 390px и desktop, Esc и закрытие по фону.
4. Выход из аккаунта: новый email не должен автоматически подставляться гостю.

**Блокер приёмки:** без тестового почтового ящика и проверки исходящего транспорта хостинга нельзя подтвердить доставку. Независимый `e2e_` пока не запускался.

## Исправление ложного ограничения отправок (28.10.2026)

Пользователь получил HTTP 429 «Достигнут лимит», хотя ни одного письма успешно не отправил. **Причина:** прежний `af_mail_rate_limited()` записывал timestamp *перед* вызовом `mail()`, независимо от его результата. Четыре безуспешных повторных попытки блокировали следующие на час.

Теперь `public/api/send-crop.php` хранит под отдельным ключом `affresco-accepted-v2` лишь события с **`mail()===true`**, защищённые файловой блокировкой на IP. Проверка лимита производится непосредственно перед попыткой передачи письма; если почтовый транспорт вернул `false`, блокировка освобождается **без увеличения счётчика**, а пользователь видит `mail_unavailable` (HTTP 503), не 429. Старые timestamp не учитываются, поэтому ложный лимит снимается сразу после деплоя. Значение 429 возможно только после четырёх принятых сервером писем за последний час. Если нет доступа на запись к счётчику, сервер возвращает отдельное `rate_storage_unavailable` (503), а не ошибочное 429.

**Проверено:** логика PHP на уровне кода и JSON-key PHP CLI; фактический POST с JPEG на продакшен и получение письма не выполнены. При повторной ошибке 503 требуется проверить `mail()` на CISHOST/ISPmanager и корректность outbound mail / SPF/DKIM; `mail()` true не гарантирует доставки в Inbox. Не выдавать это за реальное тестовое письмо.
