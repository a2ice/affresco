# 006 — Отправка выбранного кадра фрески на email

**Статус на 28.10.2026:** код реализован в `main`, приёмка реального письма в почтовом ящике и browser E2E **ещё не проведены**. Не заявлять доставку без подтверждения.

## Работающий сценарий

В редакторе вместо неинформативного «Сохранить» (кадр сохраняется автоматически) размещена кнопка **«Отправить»** с конвертом. По нажатию открывается email-попап `#emailModal`: пользователь вводит email; авторизованному посетителю адрес предзаполняется из `data/accounts.json`, но доступен для редактирования.

После отправки в браузере создаётся **настоящий JPEG выбранного кадра** через Canvas из оригинального изображения с учётом текущего zoom/положения/selection. Максимальное измерение файла — 1600 px, качество JPEG 0.80, жёсткое ограничение base64. В JSON POST на `/api/send-crop.php` уходят только email, SKU, размеры кадра и JPEG. Почтовый PHP через PHPMailer подключается к SMTP с авторизацией и TLS, формирует MIME multipart/mixed (текст, SKU, размеры и вложение `affresco-SKU.jpg`) и передаёт письмо SMTP-серверу. Окно успеха открывается **только при `HTTP 200` и `accepted:true`**; это означает приём PHP-почтовым транспортом, но не гарантирует финальную доставку в Inbox. При ответе 503 и прочих ошибках попап остаётся на экране и показывает понятную ошибку. Никакой имитации и фиксированного таймера успеха больше нет.

Без входа в систему пользователь может отправить кадр на свой адрес, но не сохраняет его в аккаунте. Для вошедшего пользователя сервер при отправке обновляет `email` в существующей записи `accounts.json`, используя блокировку файла. В личном кабинете появилась отдельная форма для редактирования и сохранения `email` через `POST /api/account-email.php`; `GET /api/auth.php` возвращает сохранённый адрес только владельцу авторизованной сессии. Пароли, хеши и полный JSON никогда не возвращаются.

### Ограничения и безопасность

- Запись `data/accounts.json` осуществляется на FTP в существующем месте; новый ключ `"email": "example@domain.tld"` создаётся у конкретной записи при первом сохранении. Значение не нужно вручную добавлять всем пользователям.
- **Обновлено:** на виртуальном CISHOST PHP `mail()` официально запрещён. Теперь используется **PHPMailer v6.10.0 + SMTP AUTH + TLS** и SMTP-ящик, созданный в ISPmanager. Нужны DNS SPF/DKIM/DMARC для доставляемости. Секреты в GitHub не коммитятся; настройки читаются из приватного FTP `data/mail.json`.
- `send-crop.php` принимает только POST с `X-Affresco-Request:1` и проверкой Origin/Fetch-Site, валидирует email/SKU/числа и содержимое JPEG. Размер файла ограничен 2.2 MB, измерения изображения — до 3200 px. Не более **4 попыток за час на IP** в приватном PHP temp storage. Не использовать этот endpoint как массовую рассылку.
- `/data/accounts.json` должен возвращать HTTP 403 при прямом запросе; хеши на FTP и email остаются серверными. `public/data/.htaccess` защищает файл на Apache, конфигурация nginx требует отдельной проверки.
- `mail()`=true означает **приём почтовым транспортом**, а не подтверждение доставки в почтовый ящик. Нельзя показывать пользователю «доставлено».

## Проверено

- Синтаксис нового JS корректен; изолированные проверки Canvas-кропа: весь кадр, уменьшенный кадр и обрезка у края — 3/3 PASS.
- Мок-сценарии submit: адрес из аккаунта подставлен, редактирование возможно, POST содержит JPEG, success only on positive API response, error leaves dialog open — PASS.
- Внешним GET оба новых PHP endpoint возвращают 405 (т.е. файл развёрнут, исполняется PHP и GET запрещён), `auth.php` без входа возвращает `authenticated:false`.
- **Не проверено:** реальная отправка `mail()`, доставка тестового JPEG на живой адрес, запись `email` в FTP `accounts.json` после авторизованного изменения, UI на iPhone Safari. Не передавать логин/пароль или личный email в документацию.

## E2E handoff для независимого тестирования

Проверять `https://affresco.a2ice.ru/`, коммиты `main` с версиями `site.js?v=email-live-20261028` и `account.js?v=account-email-20261028`.

1. Гость: открыть 6039, выделить узнаваемый фрагмент, выбрать «Отправить», указать **тестовый email**. На тестовом адресе получить письмо с JPEG и убедиться, что прикреплён именно выбранный, а не целый исходный рисунок.
2. Войти под тестовым аккаунтом с `password_hash()`, сохранить email через кабинет, обновить страницу, снова нажать «Отправить» — адрес должен подставиться. Изменить адрес в email-попапе, отправить, проверить обновление `accounts.json` и подстановку при следующем открытии.
3. Вызвать ошибку почтового транспорта в тестовом окружении — success недопустим, остаётся форма и сообщение об ошибке. Проверить формат 422 для неверного email, 429 для >4 отправок/час/IP; проверить 390px и desktop, Esc и закрытие по фону.
4. Выход из аккаунта: новый email не должен автоматически подставляться гостю.

**Блокер приёмки:** без тестового почтового ящика и проверки исходящего транспорта хостинга нельзя подтвердить доставку. Независимый `e2e_` пока не запускался.

## Исправление ложного ограничения отправок (28.10.2026)

Пользователь получил HTTP 429 «Достигнут лимит», хотя ни одного письма успешно не отправил. **Причина:** прежний `af_mail_rate_limited()` записывал timestamp *перед* вызовом `mail()`, независимо от его результата. Четыре безуспешных повторных попытки блокировали следующие на час.

Теперь `public/api/send-crop.php` хранит под отдельным ключом `affresco-accepted-v2` лишь события с **`mail()===true`**, защищённые файловой блокировкой на IP. Проверка лимита производится непосредственно перед попыткой передачи письма; если почтовый транспорт вернул `false`, блокировка освобождается **без увеличения счётчика**, а пользователь видит `mail_unavailable` (HTTP 503), не 429. Старые timestamp не учитываются, поэтому ложный лимит снимается сразу после деплоя. Значение 429 возможно только после четырёх принятых сервером писем за последний час. Если нет доступа на запись к счётчику, сервер возвращает отдельное `rate_storage_unavailable` (503), а не ошибочное 429.

**Проверено:** логика PHP на уровне кода и JSON-key PHP CLI; фактический POST с JPEG на продакшен и получение письма не выполнены. При повторной ошибке 503 требуется проверить `mail()` на CISHOST/ISPmanager и корректность outbound mail / SPF/DKIM; `mail()` true не гарантирует доставки в Inbox. Не выдавать это за реальное тестовое письмо.

## Исправления по скриншотам: валидация и файловый лимит (28.10.2026)

Владелец прислал два воспроизводимых случая:
- `a2ice@yandex` (домен без точки) проходил встроенную проверку `<input type=email>`. Это допустимо в сравнительно мягкой HTML5-проверке, но не соответствует ожидаемому формату полного публичного email. PHP уже вызывал `filter_var(..., FILTER_VALIDATE_EMAIL)` **до лимита**, но объединял эту проверку с SKU и размерами в единый `invalid_request` (HTTP 422). JS не показывал конкретную ошибку адреса, а общий текст «Ошибка отправки».
- Корректный адрес приводил к `rate_storage_unavailable` (HTTP 503): хостинг запрещал создание/запись файла счётчика в PHP-temp. Пользователь не достигал вызова `mail()` даже при нуле успешных писем.

Исправлено:
1. В `site.js` добавлена строгая предварительная проверка полного домена (например, `name@example.com`); в HTML поле снабжено `pattern` и безопасным fallback `method=post` (без утечки адреса в URL при отключённом JS). `a2ice@yandex` теперь отвергается **перед POST** с конкретным пояснением. При исправлении ввода ошибка снимается.
2. В `send-crop.php` получатель проверяется `filter_var` + полным доменным regex **до декодирования JPEG, лимитов, изменения аккаунта и `mail()`**. Некорректный адрес возвращает отдельное `{"error":"invalid_email"}`, HTTP 422.
3. Квота — максимум четыре **принятых почтовым транспортом** письма за час; отказы `mail()` не считаются. Сначала используется приватная директория выше `public`, затем доступная PHP-temp. Если обе недоступны на конкретном хостинге, **демонстрационный fallback — квота PHP-сессии**, а не полная блокировка всех отправок `rate_storage_unavailable`. При таком fallback ограничение действует на сессию, а не на IP — это временный компромисс для демосайта, не решение для открытого массового сервиса.
4. Исправлены сообщения об ошибках `invalid_request` и `invalid_image` и версия JS: `site.js?v=mail-validation-rate-fallback-20261028`.

**Проверки:** JS проверен на синтаксис, девять тестовых адресов (включая оба случая пользователя) правильно принимаются/отклоняются; эквивалентная серверная регулярка и `filter_var` проверены в PHP CLI на четырёх типах доменов; структурно подтверждено, что валидация идёт перед квотой, а при недоступных файловых директориях используется session fallback. **Пока не подтверждены:** реальный POST с JPEG после обновления, вызов `mail()` на хостинге и доставка письма. `Dmitanium` офлайн, внешний интерактивный браузер недоступен. Возможная следующая ошибка `mail_unavailable` означает, что нужно настроить исходящий транспорт хостинга, а не продолжать менять квоту.



## SMTP вместо запрещённой PHP mail() — 28.10.2026

### Подтверждённая причина ошибки

На скриншоте с корректным получателем `a2ice@yandex.ru` сервер возвращал `mail_unavailable`. Проверка [официальной базы знаний CISHOST](https://www.cishost.ru/faq/shared-hosting), раздел «Настройка почтовых форм и скриптов отправки», установила: **на виртуальном хостинге `mail()` запрещена; нужна SMTP-авторизация почтовым ящиком домена**. Прежние правки валидатора/лимита не могли устранить эту инфраструктурную причину. На CISHOST перечислены порты 25, 587 (STARTTLS) и 465 (SSL). Наиболее предпочтителен **587 + STARTTLS**.

### Выполнено

- В `public/api/vendor/phpmailer/` подключена PHPMailer 6.10.0 из официального репозитория с `LICENSE.txt` (LGPL-2.1), без Composer на FTP.
- `public/api/_smtp_mail.php` читает SMTP-конфигурацию из `../data/mail.json` **вне web-root**, либо из совместимого FTP-пути `public/data/mail.json`, защищённого `public/data/.htaccess`. Не использует более PHP `mail()`. Поддерживает `587/starttls`, `465/ssl` и `25/starttls` с проверкой TLS-сертификата.
- `public/api/send-crop.php` сохраняет прежнюю валидацию JPEG/email, лимит только принятых сообщений и защиту от CSRF, но передаёт JPEG и метаданные на SMTP через PHPMailer. Email в аккаунте обновляется **после принятия письма SMTP**, чтобы не считать неудачную отправку сохранённой. Ответ `accepted:true` означает приём SMTP-сервером, не гарантирует доставку.
- Форма email помечена `novalidate`, оставлена проверка JavaScript + серверная, сообщения показываются **под полем**, без двух разных браузерных и собственных предупреждений. В UI добавлены отдельные понятные ошибки `smtp_not_configured`, `smtp_invalid_config`, `smtp_auth_failed`, `smtp_unavailable`.
- `/data/accounts.json` остаётся отдельно от `/data/mail.json`, SMTP-пароль нигде не возвращается и не логируется.

### Что требуется в панели CISHOST

В ISPmanager открыть **«Почтовые домены»**, добавить/проверить почтовый домен отправителя и включить DKIM; затем в **«Почтовые ящики»** создать или выбрать реальный почтовый ящик. Для отправки нужна пара *полный email почтового ящика + его пароль*.

В FTP рядом с `data/accounts.json` создать **`data/mail.json`**, используя безопасный шаблон [mail.example.json](mail.example.json), подставив фактические SMTP-host, логин, пароль и email отправителя (обычно `from` = `username`):

```json
{
  "host": "mail.example.com",
  "port": 587,
  "security": "starttls",
  "username": "no-reply@example.com",
  "password": "ВАШ_ПАРОЛЬ_ОТ_ПОЧТОВОГО_ЯЩИКА",
  "from": "no-reply@example.com",
  "from_name": "AFFRESCO"
}
```

**Это пример, а не реальные данные CISHOST.** Имя `host` нужно взять из настроек конкретного почтового домена, пароль хранить **только на FTP**, не вставлять в GitHub, чат и скриншоты. Если файл лежит в публичном `data/`, HTTP GET `/data/mail.json` должен возвращать **403** (проверять только статус, не раскрывая содержимое). При отсутствии файла SMTP API возвращает `smtp_not_configured`, а не фиктивный успех.

### Приёмка

**Код и структура:** PHPMailer, TLS-конфиг, валидация SMTP-настроек, POST с JPEG и отдельные сообщения ошибок проверены адресно; JavaScript прошёл синтаксическую проверку. **Фактический SMTP-логин / получение JPEG:** пока не проверены, потому что почтовые реквизиты на FTP ещё не настроены и удалённый компьютер недоступен. До подключения почтового ящика этап «Реальная отправка» **НЕ ПРИНЯТ**.

Сценарий E2E: после настройки `mail.json` отправить кадр SKU 6039 на выделенный тестовый адрес, проверить `HTTP 200 accepted:true`, реальное получение JPEG во вложении и соответствие выбранному фрагменту. При `smtp_auth_failed` проверить пользователя/пароль, при `smtp_unavailable` — порт, хост, TLS и исходящие подключения, при `smtp_not_configured` — путь файла. Не передавать секреты ассистенту.


## Локальный SMTP CISHOST без TLS — 28.10.2026

По [инструкции CISHOST](https://blog.cishost.ru/2014/07/18/ob-otpravke-pochty.html) скрипты на хостинге могут использовать SMTP AUTH через `localhost:25` без TLS. Для этого добавлено явное значение `"security": "none"`: оно разрешено **только** при `host=localhost` и `port=25`. В этом режиме отключены как обязательный STARTTLS, так и автоматический STARTTLS PHPMailer. Внешние SMTP по-прежнему требуют TLS с проверкой сертификата; автоматического отката на незашифрованное соединение нет.

Для созданного ящика `affresco@a2ice.ru` на FTP в существующем `mail.json` установить:

```json
{
  "host": "localhost",
  "port": 25,
  "security": "none",
  "username": "affresco@a2ice.ru",
  "password": "ПАРОЛЬ_ЭТОГО_ЯЩИКА_ТОЛЬКО_НА_FTP",
  "from": "affresco@a2ice.ru",
  "from_name": "AFFRESCO DEMO"
}
```

Замена ящика при прежних `localhost:587/starttls` сама по себе транспорт не исправляет. Сначала требуется развернуть поддержку `none`, затем изменить конфиг. Статья от 2014 года не подтверждает доступность этой схемы на конкретном текущем сервере: реальная SMTP-авторизация и получение JPEG остаются непроверенными до повторной отправки. При сохранении ошибки проверить приватные логи хостинга/почтовую очередь без публикации SMTP-пароля.
