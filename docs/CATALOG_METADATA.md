# AFFRESCO — каталог фресок и размеры

**Обновлено:** 28.10.2026  
**Статус:** 19 артикулов заполнены редакционными черновиками; размеры ориентировочные и **не подтверждены производителем**.

## Каталоги на FTP

- `/Images/catalog/` — **оригиналы** с линейками и размерами, не удалять и не перезаписывать при подготовке.
- `/Images/catalog/Prepared/` — **основная фактическая структура** подготовленных изображений, загружаемых владельцем. Если исходная папка названа кириллицей, используется `/Images/каталог/Prepared/`. Также поддерживаются варианты со строчным `prepared` и прежняя `/Images/prepared/`. Все пути чувствительны к регистру букв на Linux.
- Исходное имя файла без расширения — **артикул**, уникальный идентификатор фрески. Например, `AB-123.jpg` и `AB-123.webp` относятся к одному артикулу `AB-123`.
- Допускаются разные расширения между оригиналом и подготовленным вариантом. Регистр символов в артикуле должен **совпадать**.
- Если подготовленного изображения для артикула пока нет, сайт временно показывает оригинал. Когда подготовленное появится в соответствующем вложенном каталоге, `/api/catalog.php` автоматически отдаст его вместо оригинала. При отсутствии оригинала подготовленный файл тоже включается в каталог.
- Фотографии на FTP не копируются в репозиторий; GitHub Actions исключает `Images/**` из синхронизации.

Проверка: откройте `https://afreska.2ice.ru/api/catalog.php` — поле `items[].image` должно начинаться с `/Images/catalog/Prepared/` (или выбранного фактического пути), а `items[].prepared` должно быть `true`. При ручном редактировании `catalog.php` только на FTP правка может быть перезаписана следующим деплоем из GitHub `main`.

## Структура JSON

Файл: [`public/data/catalog.json`](../public/data/catalog.json).

```json
{
  "version": 1,
  "unit": "cm",
  "items": {
    "ART-001": {
      "name": null,
      "description": null,
      "width_cm": 300,
      "height_cm": 200,
      "orientation": "landscape",
      "dimensions_estimated": true,
      "editorial_status": "draft_unverified_image"
    }
  }
}
```

**Это только пример схемы, `ART-001` не является реальным артикулом.** В реальном файле перечислены 19 фактически обнаруженных в API артикулов, а названия, описания и размеры — творческий черновик по разрешению владельца. Величины `width_cm`/`height_cm` — примерные форматы для демонстрации, не изготовительские характеристики.

- Ключ объекта `items` = **точный артикул** (имя изображения без расширения).
- `name` — согласованное **название фрески** (строка); пока неизвестно — `null`, не подставляем придуманное название.
- `description` — согласованное **краткое описание фрески** (строка); пока неизвестно — `null`. В режиме «Списком» описание видно рядом с изображением, а в режиме компактных мобильных карточек может скрываться ради читабельности.
- `width_cm` — **ширина** фрески в сантиметрах; при `dimensions_estimated: true` это редакционная оценка, а не подтверждённый физический размер. Подтверждать по линейке оригинала/поставщику перед коммерческим использованием.
- `height_cm` — **высота** фрески в сантиметрах; при `dimensions_estimated: true` тоже приблизительная. Нельзя считать размер достоверным только по пикселям.
- `dimensions_estimated` — `true`, когда размеры условные; интерфейс отображает знак `≈` и поясняет неопределённость. Для точного размера после проверки следует поставить `false` и уточнить значения.
- `editorial_status` — `draft_visual_review` (сюжет ориентировочно сопоставлен со скриншотом) или `draft_unverified_image` (авторское нейтральное название и описание без визуального просмотра оригинала); это не пользовательский статус и не подтверждение авторства.
- `orientation` — независимая дополнительная классификация: `landscape` = горизонтальная, `portrait` = вертикальная, `square` = квадратная. Пока не подтверждена — `null`. Не делать вывод о физическом размере по пикселям и не определять ориентацию по пропорциям файла с интерфейсными полями.
- `null` — значение ещё не проверено, **не ноль**. Допускается заполнение полей в несколько заходов. Не подставлять размеры произвольно и не подменять их размерами стены в редакторе.
- JSON не содержит паролей или других частных данных — файл открыт для чтения браузером через `public/`. Аккаунты будут в отдельном приватном хранилище.

## Как передавать данные под диктовку

Для каждого изображения: **артикул → название → краткое описание → ширина (см) → высота (см) → ориентация → признак приблизительности**. Если ориентация или одно из измерений неизвестны, соответствующее поле остаётся `null`. После ввода сверяем артикул, не путаем горизонталь и вертикаль, проверяем валидность JSON. Все записи делаем непосредственно в `main`.

## Что возвращает API

`GET /api/catalog.php` формирует `items[]` из файлов на FTP, дополняя каждый элемент из JSON по артикулу:

- `sku`, `name`, `description` — подтверждённые данные или `null` (не выдумывать);
- `image` — путь к `prepared` при наличии, иначе к `catalog`;
- `original_image` — путь к оригиналу или `null`;
- `prepared` — логический признак;
- `width_cm`, `height_cm`, `orientation` и `dimensions_estimated` — размеры, классификация и явный признак приблизительности (ориентация может быть `null`).

Файл не меняет физические изображения. Указанные размеры относятся к исходному рисунку фрески, а не к пользовательскому кадру после crop.

## Отображение метаданных в карточках и редакторе (28.10.2026)

- В карточках большого каталога и попапа выбора порядок: **название → отдельная кнопка «Арт. SKU» → размеры → описание**. Нажатие на артикул копирует только сам SKU в буфер и вызывает toast «Артикул скопирован», не открывая редактор; фотография/название/«Кадрировать» открывают редактор независимо.
- В редакторе `#wallWidth` и `#wallHeight` при **первом выборе SKU** получают `width_cm` и `height_cm` этого SKU из `/api/catalog.php`. Фактические пропорции фотографии не заменяют значения из каталога при обработке `onload`.
- Если уже существует сохранённый crop-черновик для артикула, его ширина/высота и выбранная рамка имеют приоритет над начальными размерами каталога. Если размеров в JSON нет, сохраняется fallback по пропорциям изображения.
- При `dimensions_estimated: true` карточка показывает знак `≈`, а редактор текстом поясняет, что значения ориентировочные и допускают изменение. Это не утверждение о реальных максимальных размерах печати.
- Поиск `#catalogSearch` в sticky-панели поддерживает ввод названия и артикула, подсказки и фильтр каталога, включая избранное. Текстовые данные достаточно обновлять в `public/data/catalog.json`; JS и API менять не нужно.

## Максимальные размеры при изменении области кадра (28.10.2026)

По замечанию владельца в `site.js` закрыта ошибка: при увеличении выделения после предыдущего уменьшения ширина/высота пересчитывались относительно сохранённого размера, но ограничивались общими 1000 см, а не размерами артикула. Теперь `sizeLimits()` читает `catalogDimensions(currentItem)` и применяет индивидуальные пределы `width_cm` и `height_cm` при drag/keyboard resize, ручном вводе и выборе соотношения сторон. Поля `#wallWidth` и `#wallHeight` получают HTML-атрибуты `max` равные размерам текущего SKU; попытка ввести больше отклоняется с пояснением допустимого диапазона. Старые `custom` черновики с превышением величин тоже ограничиваются до JSON при открытии, а нормальные пользовательские размеры остаются.

Пример: у SKU 6039 максимально `320 × 220 см` — увеличение области не выводит значения за пределы этих чисел. Это ориентировочный демонстрационный максимум из `catalog.json`, а не документально подтверждённый предел изготовления.

В разметке редактора удалён `.editor-settings-header`; в `.editor-heading` под «Ваш кадр фрески» добавлена подпись «Настройте размер фрески»; заголовок имеет `font-size:32px` и на мобильных устройствах тоже.

**Кодовые проверки:** 19/19 записей JSON — PASS для запрета превышения через масштабирование рамки, проверки полей и четырёх предустановленных пропорций; 3/3 случая загрузки сохранённых черновиков — PASS (устаревший сверхлимитный, допустимый custom, metadata отсутствуют). JS синтаксически корректен. Фактический iPhone/desktop E2E с перетаскиванием и визуальным сравнением ещё не подтверждён.

## Исправление подстановки размеров и миграция черновиков (28.10.2026)

**Причина замечания владельца:** прежний `openEditor` подставлял `width_cm`/`height_cm` из JSON только при отсутствии сохранённого черновика; старые `localStorage`-черновики с историческими `300 × 225 см` сохраняли свои размеры и перекрывали JSON. Дополнительно кнопка «Восстановить исходный кадр» вновь ставила ширину `300 см`.

**Теперь:** `catalogDimensions(item)` определяет ширину и высоту непосредственно из текущего элемента `/api/catalog.php`. Открытие редактора для любого SKU использует размеры каталога даже при существующем черновике прежней версии; позиция и геометрия сохранённого кадра остаются. Новая настройка `dimensionsSource: "custom"` явно отмечает **последующие ручные изменения** чисел, соотношения сторон или размеров рамки — такие пользовательские значения сохраняются при следующем открытии того же SKU. Исторические черновики без этой метки мигрируют к JSON-размерам, поскольку нельзя надёжно отличить старые автоматически выставленные значения от введённых человеком. «Восстановить» возвращает именно размеры каталога (если они существуют), а не `300 см`. Если метаданных нет, сохраняется запасное поведение по соотношению сторон снимка. Предупреждение об ориентировочных размерах выводится только для каталожных значений, не для явно пользовательских.

**Фокус в UI:** в `public/assets/css/editorial.css` единая рамка для всех прямоугольных полей (`input` типа text/search/number/password/email и т. п., `textarea`, `select`). Внешний `outline` при фокусе не добавляется, меняется только цвет исходной границы; чекбоксы, радиокнопки и ползунок сохраняют штатный индикатор клавиатурного фокуса. Это касается и поиска в закреплённом каталоге, и поиска в попапе, и размеров редактора.

**Проверка:** 19/19 SKU: начальные значения и значения после `image.onload` совпадают с JSON; старый черновик 300×225 для арт. 6039 мигрирует к 320×220; новый `custom`-черновик сохраняет 420×240; «Восстановить» возвращает 320×220. Все проверенные сценарии PASS. Статический JS синтаксически корректен. Публичные JS/CSS с новыми правилами доступны, но визуальный браузерный E2E на iPhone ещё не подтверждён.
